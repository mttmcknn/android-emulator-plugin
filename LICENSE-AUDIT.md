# Release license audit

Updated on 2026-10-09 for release `2026.10.9`, reconciling upstream main `75bfbeb927feb2c0c98a134fbc30c303f4b5f916` with the prepared submission branch at `616bbf30b0e054ec2e931a13277d4810e850fae5`. The original dependency and binary inspections below were performed on 2026-10-08; their dates and immutable evidence are retained. This is an engineering inventory and compliance review, not a legal guarantee. The project's existing Apache-2.0 license is retained; third-party code and artwork retain their own terms.

## Distribution scope

`scripts/build-plugin.mjs` copies `runtime/` into `plugins/android-emulator-plugin/runtime/`, copies every file in root `assets/screenshots/` into the plugin's `assets/screenshots/`, retains root LICENSE/NOTICE at plugin and runtime boundaries, and synchronizes the plugin version. Codex installs the plugin directory, so notices must exist inside that directory. The three screenshots now ship in the installable plugin as well as repository/source archives; the manifest lists them as `interface.screenshots`. A repository/source archive additionally contains the root README, tests, and build/release scripts. The local submission packager includes the committed plugin files, a copy of this audit, and preparation information, with a separately applied listing/review metadata overlay. It does not bundle installed dependencies or publish by itself.

The original checkout had no archive builder. Neither the original nor reconciled release has npm dependencies, vendored `node_modules`, or checked-in host scrcpy/FFmpeg/SDL/ADB executables. Runtime JavaScript imports Node built-ins and local modules; the browser uses local JavaScript/CSS and system fonts. New main-branch device-pinning, connected-device discovery, comparison tabs and screen-label behavior add first-party source, not a new shipped dependency. Connected phones also use the user's ADB installation and the same bundled Android server; no phone firmware or SDK payload is copied into this release.

The sole initially bundled executable payload is the Android scrcpy server. The plugin speaks its protocol through its own JavaScript client and uses browser WebCodecs. Android SDK tools are discovered from the user's SDK; optional FFmpeg/ffprobe are found on PATH. Node is taken from Codex or PATH. Those installations are not redistributed by the plugin.

Navigation is a separate case: `runtime/core/backends/navigation-dependencies.mjs` can download Minimap and Google's Android CLI into its managed cache, then run them. They are not in the plugin archive, but their acquisition and later runtime components are part of this audit. Existing user-installed overrides and PATH tools are distinguished from downloads made by the plugin.

## Managed Android CLI: launcher, payload and terms

[Google's download page](https://developer.android.com/tools/agents/android-cli/download) supplies the plugin's direct launcher URL and an [official installer](https://dl.google.com/android/cli/latest/darwin_arm64/install.sh). That installer downloads `android`, then runs it for a first download. It was read, not run. The plugin independently performs a similar first launch while checking `--version`.

The macOS arm64 launcher fetched on 2026-10-08 is a roughly 3.5 MB Mach-O file, SHA-256 `52618946fb521fa08de5729181d12cb9190a5d6a2e8e869f71799808bc82792e`, exactly matching the plugin's pin. Static strings identify a second URL, [latest/darwin_arm64/android-cli](https://dl.google.com/android/cli/latest/darwin_arm64/android-cli), and launcher metadata `1.0.16500706`. The launcher cache path/version check does not constrain the second download to the launcher's SHA or to an immutable release. Thus the existing checksum pins the launcher, not the effective runtime.

The effective payload was separately downloaded without execution for static inspection: 89,565,808 bytes, SHA-256 `204aeb6f8ad5420176cbc2d9a9c57e8108cbf42c62a17146650eba5552880c22`. Its embedded `main.jar/METADATA` reports version `1.0.16500706`. Its embedded ZIP contains 168 entries including `main.jar`, `lib/libdownloader_jni.dylib`, and a JRE whose release metadata identifies Java 25.0.4. The JAR's LICENSE starts with Copyright 2024 The Android Open Source Project/Apache-2.0. Its additional notices include ISC/MIT and Lucene material; interaction notices name BoofCV, GeoRegression, DDogleg, EJML and Commons IO. The JRE retains GPLv2, Classpath/assembly exceptions and its third-party notices. The upstream files are downloaded intact; no legal files are removed.

Static inspection of `com/android/cli/ui/Tos.class` established the exact mechanism: `showIfNeeded()` returns when Java property `android.cli.dir` is absent or `<cliDir>/tos_displayed` trims to `1`. Otherwise it prints the SDK terms/privacy/metrics notice to stderr, then writes `1` to the display marker (I/O errors are swallowed). There is no yes/no prompt, stdin read, acceptance call or consent verification in this method. `AndroidCli.execute()` invokes it before command processing, including `--no-metrics --version`. The plugin's successful version-check subprocess captures stderr without showing it, and its private `ANDROID_USER_HOME` isolates this marker from the user's normal CLI state. Thus first-use terms can be displayed only into captured stderr and still marked displayed. That is a confirmed disclosure problem; `tos_displayed` records display, not agreement.

The current [SDK terms](https://developer.android.com/studio/terms), dated April 28, 2026, require agreement before use (§2.1), permit assent by clicking or use (§2.2), require authority when binding an entity (§2.4), preserve open-source component terms (§3.5), prohibit notice removal (§3.8), and allow changed terms with new versions (§13.1). Matt's existing normal CLI display marker and SDK license files predate this audit and establish prior installation/license state, not who agreed or applicability to this newer payload/terms. No agreement or marker was created or changed here, and the CLI was not executed.

The README now discloses direct upstream downloads and the launcher's further runtime download even during version checks. The emulator skill explains first-use terms, honors already established user agreement instructions, and directs the user to handle any new agreement themselves. Existing `ANDROID_EMULATOR_ANDROID_CLI` overrides remain available. These documentation fixes do not prove consent or turn a display marker into it. Matt should confirm the applicable agreement/use basis before first managed navigation use in his context; future users need their own basis. This is a user-use question, not a confirmed release-license incompatibility.

Neither launcher, JAR, JRE nor native payload is in either plugin or source release archive, and the plugin does not mirror them to recipients. Downloading upstream software into a user's cache is distinct from redistributing that software in the plugin. Consequently, this inspection establishes no plugin breach of SDK redistribution restrictions, no plugin JRE/GPL source-offer omission, and no need to relicense the plugin under GPL. A full version-to-license mapping of this moving external runtime remains unavailable; these observed terms cannot guarantee the next `latest` payload. Any future bundling/mirroring would require a fresh redistribution and source/offer audit of the exact bytes.

## Confirmed fixes, evidence limits and publication boundary

Confirmed notice gaps in the original plugin were its installable first-party legal files, embedded scrcpy/Kotlin notices, Android robot attribution, and managed Minimap application/runtime notices. Those are now repaired. The Minimap upstream one-file archives themselves still omit notices; this repository's downstream fix does not alter them. No remaining incompatible license or unmet copyright notice/source-offer obligation has been identified in the actual inspected plugin archive after the fixes.

Three matters remain factual or precision limits, rather than demonstrated violations: (1) the user's agreement/use basis for the external Google CLI and the changing effective payload; (2) product-name context/authorization and authentic screenshot/edit/wallpaper/disclosure facts; (3) a binary-level Minimap SBOM finer than the matched source/build and exact upstream runtime notice superset. The Google CLI hidden first-use display and unpinned second download are confirmed implementation properties, now documented; documentation cannot establish user agreement. These limits prevent an unconditional end-to-end legal guarantee. They do not establish that distributing the repaired plugin code/archive is unlawful, or justify removing functionality/assets without Matt's decision.

No third-party work was relicensed, no top-level license changed, and no agreement accepted in this audit. The 2026.10.9 task separately authorizes a GitHub release and Library delivery; it does not authorize Registry submission or remote CI. Release publication status and the final archive verification belong to that release record. This audit does not claim they have already occurred.
